今天这一场从下午干到晚上，围绕一件事：**把桌宠的拖拽摆动换成正经物理，并把它落地进项目。**

下面是完整经过。我尽量把做对的、做错的都写清楚，尤其是错的那部分——那才是下次能省时间的地方。

## 一、起点：一个跨设备不一致的问题

用户提出的第一句话就把问题定死了：

> 目前的拖拽摆动完全基于鼠标每频率的位移距离，而不是基于速度或者加速度等正经物理公式计算，导致不同设备的拖拽效果差异十分巨大。

我把原公式翻出来看，确实是这样：

```python
dTheta = dx * self._amplifier + 0.5 * (-0.5)
```

`dx` 是「距上一个鼠标事件移动了多少像素」。也就是说，**这里的"角度"其实是"事件间隔内的位移"，而不是物理量**。同一段 0.4 秒、600 像素的拖动轨迹，我实测过：

| 鼠标事件率 | 峰值角 |
|---|---|
| 125 Hz | 15.88° |
| 250 Hz | 7.88° |
| 1000 Hz | 1.88° |
| 8000 Hz | 0.13° |

**同一动作差 122 倍。** 这不是调参能救的，公式本身量纲就不对。

## 二、先搭模型，再动代码

我没有直接改项目代码，而是先写了一个独立的仿真工具 `sim_pendulum.py`，把物理模型单独拎出来做参数实验。

模型是**绕抓取点转的阻尼单摆**：

```
θ'' = -(g/r)·sinθ - 2ζω₀·θ' - (ka·ax·cosθ - ka·ay·sinθ + kv·vx·cosθ - kv·vy·sinθ)/r
```

其中 `r` 是抓取点到贴图中心的距离（摆长），`ax/ay` 和 `vx/vy` 是光标的加速度和速度。

一开始我只有"加速度通道"（重力回复 + 光标加速度驱动），但效果不好：手一抖就晃。于是试了几种补强：

- **加速度低通（τ_a）** —— 压掉差分噪声
- **速度通道（kv）** —— 关键发现：手抖在**速度**上是零均值的，所以速度通道天然抗抖

做了五组预设跑对比，用两个指标衡量：

- **跟手**：故意甩一下时角度峰值够不够大
- **抗抖**：匀速拖动时角度的抖动量

| 预设 | 跟手 | 抗抖 | 信噪比 |
|---|---|---|---|
| A 原始加速度 | 19.9° | 8.8° | 2.2 |
| B 加速度低通 | 17.0° | 6.3° | 2.7 |
| **C 速度扶正** | **23.8°** | **5.0°** | **4.8** |
| D 纯速度驱动 | 31.6° | 4.7° | 6.7 |
| E 高阻尼 | 14.4° | 5.3° | 2.7 |

用户选了 **C**：`ka=0.4, kv=3.0, τ_a=0.10, ζ=0.35`。理由是"喜欢 C 甩起来的手感"——比 D 收敛一点，比 A 跟手得多。

**中途也走过弯路**：我还试过一版"刚体 + 软约束"模型（把宠物当成被弹簧拴住的刚体），建完实测发现抗抖 38~54°、信噪比 0.5，比 D 差十倍。原因是弹簧要够硬才跟得上手，而够硬就意味着手抖也一起进去了。**这条路线被证伪后删掉了**，代码里没留。

## 三、落地时撞到的一堆问题

拿 C 预设接进项目之后，真正的工作才开始。按时间顺序：

### 1. 摆动幅度大时贴图被窗口裁掉

窗口是固定的 689²，而大角度摆动需要的空间是"抓取点到贴图最远角的距离"，抓角时能到 621px。**四角会被裁掉。**

解决思路：**让窗口按需要自适应**——按下时算出 R，把窗口撑成 2R²，并把抓取点摆在窗口正中，这样窗口中心就是旋转轴心，几何上保证不裁切。

### 2. 松手后宠物不脱钩

改完之后出现一个更严重的问题：松开左键，宠物继续跟着鼠标跑。

我先猜是"释放事件丢了"，用户说"不存在这种可能性"。后来我说"那我们加一行 print 验证"——**结果是：没有打印。**

释放事件确实没送达。原因是我在 `mousePressEvent` 里 resize + move 了窗口，**把 Qt 的隐式鼠标抓取冲掉了**。修法是几何变更之后显式 `grabMouse()`，收尾时 `releaseMouse()`。

> 这件事的教训我记在下面第四节。

### 3. 松手瞬间贴图位移

按下时我补偿了贴图位置，**松手时忘了补**。窗口从 2R² 缩回 689²，贴图就跳了 `_spriteOrigin - _spriteInset` 那么远。

### 4. 边缘 clamp 把宠物推到够不着的地方

这是我改动引入的真 bug。原来用户有一段保护：

```python
margin = self.MARGIN * self._petImageSize // 2
if xPos < 0 - margin: xPos = 0 - margin
```

它保护的是**窗口**，因为窗口比贴图大，等价于贴图基本留在屏内。我换成了保护**枢轴点**：

```python
if xPos < -R: xPos = -R
```

**枢轴在屏内 ≠ 宠物在屏内。** 宠物是挂在枢轴上的，抓右下角再拖到屏幕左上角，枢轴勉强在屏内而贴图整个跑到屏幕外——**鼠标再也够不着了**。

用户当场纠正我：

> 你别管窗口多大，只计算拖拽点与宠物正常情况下的图片四条边的差距，然后确保这四条边不能出框不就好了

对。改成直接算抓取点到贴图四边的距离，把这四条边各自限制在屏幕内。

### 5. 这个 clamp 又不对——宠物是转的

改完还是别扭：抓左边时宠物往下坠（转过去了），移到右边就不对。

因为我又用了**"立正朝向"的四条边**，可宠物实际是旋转的，包围盒跟着角度变。用户说：

> 你把判定改成宠物在被抓住后，包裹被旋转后的图形的最小矩形

改成取四个角按当前绘制角度旋转后的 min/max 作为包围盒。同时加了松手时的归位：立正后有一两个角出界，就按最小平移距离推回屏内。

### 6. 对话泡泡的位置

先发现一个 25px 的单位错误（`MARGIN*_petImageSize//2` 算出来 100，而真实内缩是 125）。改完发现**根本没修好，偏了 500 多像素**。

真因是：`mousePressEvent` 会先把窗口撑成 2R **再**触发点击对话。泡泡出生那一刻贴图在 `_spriteOrigin`（抓角落时可达 621），泡泡却按"贴图在 125"来算。**"当窗口被调整时"就是字面意思。**

用户又补了一刀：

> 你忽略了反转和抓住侧面的情况。所以我说你把对话泡泡放到旋转后的图片的上界

于是我把"贴图相对窗口中心往四向伸出多少"抽成一个公共方法 `_spriteExtents()`，**clamp 和泡泡共用它**，两者不可能再各算一套。

### 7. 点一下会闪

最后一个，也是磨得最久的。

- 第一轮我以为是 `resize()` 和 `move()` 是两次 `SetWindowPos`，合并成 `setGeometry` —— **没好。**
- 用户指出：**"看起来要 resize 的话处理得再快都不可避免"**。对，尺寸变更本身就要重建窗口表面。
- 那就**彻底不 resize**：窗口边长一次定死为 `2 × 贴图对角线`（439² 的贴图 → 1242²），贴图居中。窗口中心到贴图最远点就是对角线，所以任意角度都不裁切——**保证比原来按抓取点算 R 更强**。之后拖拽全程只 `move()`。

- **还是闪。** 我列了四种可能让用户分类，他答：**"宠物位置跳了一下，就连对话泡也跟着一起移动了"**。

  这句话直接指向了根因：**我把窗口中心当成了旋转轴心**，所以按下时必须把窗口挪到光标处——抓边角时窗口平移最多约 440px。宠物自己没动，但窗口动了，泡泡跟着窗口走。

  修法：**轴心根本不必在窗口中心。** 新增 `_pivotOffset` 记录抓取点在窗口内的位置，`paintEvent` 绕它旋转，按下和松手都不再移动窗口。

## 四、我犯的错（这条最重要）

今天我在同一个坑里摔了不止一次，值得单独写下来：

### 1. 我反复"测错了对象"

- 边缘 clamp：我量的是**贴图**的屏幕位置，一直是 0，所以我以为没问题。**该量的是窗口位置。**
- 闪动问题：我同样一直在量贴图位置。用户一句"连对话泡也跟着移动"才让我意识到窗口在动。

**教训：验证时要问自己"用户看到的是什么"，然后量那个东西，而不是量我方便量的东西。**

### 2. 我用"复现公式"冒充"验证代码"

有一轮我写了独立脚本把 clamp 公式重抄一遍跑扫描，报告"0 越界"。但**那段脚本根本没读项目文件**——代码要是没改对，我的扫描照样通过。

后来我改成用假的 `QCursor` 驱动**真正的** `_petDraggedMove`，才算数。

### 3. 我合成测试的可信度有限

`tests/test_click_behavior.py` 里三个用例长期失败（拖拽相关），根因是 `_petDraggedMove` 轮询 `QCursor.pos()`，**合成鼠标事件驱动不了**。我用 `QApplication.sendEvent` 直塞事件，**正好绕过了整条路由**——所以"松手事件丢失"这个 bug 我一开始死活复现不出来，用户那边却稳定复现。

### 4. 我不该在信息不足时硬猜

"松手不脱钩"我猜了两轮，赔进去两次修改。"闪动"我猜了两轮。最后解决问题的那两次，都是用户给了一句**具体的现象描述**，我立刻就能定位。

**下次遇到反复出现的现象，应该早点停下来要事实，而不是继续改。**

## 五、最终结果

- **摆动**：阻尼单摆 C 预设（`ka=0.4 kv=3.0 τ_a=0.10 ζ=0.35 g=6400`），固定 80Hz 步进，时间驱动。**鼠标事件率不再参与**——跨设备差异从结构上消失了。
- **窗口**：恒定 1242²（= 2 × 贴图对角线），贴图居中，拖拽期间只移动不改尺寸。
- **轴心**：`_pivotOffset`，按下/松手窗口都一动不动。
- **边缘**：按**旋转后包围盒** clamp，四条边不出框；松手按最小平移归位。
- **泡泡**：贴在旋转后图片的上界，和 clamp 共用 `_spriteExtents()`。

交叉核对（拿仿真里已公布的数字验端口）：

| 项目 | 仿真 | 端口实测 |
|---|---|---|
| 摆长 r（抓 110,150） | 129.7 | 129.69 |
| 恒速 600px/s 稳态后仰 | `atan(kv·v/g)` = 15.71° | 15.71° |
| 抓取点/窗口位移 | — | 5 个抓取点全为 0px |
| 旋转包围盒越界 | — | 抽样 40 次 / 30 种角度，0 次 |

## 六、遗留（都不急）

1. **`_amplifier` 成了死设置** —— `config.json` 里的 `amplifier` 还在读，但换成物理之后再没人用。要么删掉设置项，要么接成摆动的总体增益。
2. **`_wandering` 的边距** —— 它用 `mainWindow.size().width()` 算边界，窗口从 689 变成 1242 之后，宠物自动走动时会离屏幕边缘更远。需要实测一下要不要调。
3. **`_settingMenuMove` 的位置** 同理，可能偏了。
4. **回归测试覆盖缺口** —— 拖拽那条链路合成事件测不了。要恢复覆盖得把光标来源抽成可替换的方法（比如 `self._cursorPos()`）。
5. **`sim_pendulum.py:141`** 有个拼写错误（`alph5a` 应为 `alpha`），跑 `--compare` 会 NameError。那个是临时脚本，用户说不管它。
6. **改缩放的瞬间还是会闪** —— 那时确实要 resize。属于手动操作，可接受。
