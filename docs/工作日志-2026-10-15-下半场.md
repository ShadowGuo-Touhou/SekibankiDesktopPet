## 二、音频：两次选型，每一步都靠实测

### 第一次选型

素材里 `click.mp3` 是 mp3、`talk.wav` 是 wav。我先测了后端能力：

| 检查 | 结果 |
|---|---|
| `QSoundEffect` 放 `click.mp3` | ❌ 解码失败 |
| `QSoundEffect` 放 `talk.wav` | ✅ Ready |
| `QMediaPlayer` 放三者 | ✅ 都能解 |

再测延迟（到 `PlayingState` 的耗时）：

| 场景 | 中位 | 最差 |
|---|---|---|
| `QMediaPlayer` 预热后 `play` | 0.02 ms | 0.02 ms |
| **`QMediaPlayer` `stop+play` 重触发** | **277 ms** | **666 ms** |
| `QSoundEffect` `play` | 0.35 ms | 245.87 ms |

点击音效必然反复重触发，所以选了 `QSoundEffect`，代价是 `click.mp3` 得转格式。ffmpeg 转出来 42,066 B / 0.26 s，实测能被 `QSoundEffect` 加载。

### 第二次选型：真正的坑

动画做完之后，用户反馈"能听到声音，但看不到动画"。查下来是这样的：

`_startSquash` 里时钟先起、再调 `_playSound`，而 **`QSoundEffect.play()` 会阻塞调用线程**：

| 后端 | `_playSound('click')` 耗时 | 动画实际帧数 |
|---|---|---|
| `QSoundEffect` | **678.5 ms** | **1** |
| `QSoundEffect`（第二次） | **242.7 ms** | **1** |
| 静音替身（我此前的所有测试） | 0.0 ms | 14 |
| `winsound` 异步 | 0.479 ms | **16** |

事件循环被冻住 → 定时器一帧都发不出来 → 第一个 tick 算出的 `elapsed` 已经超过动画总时长 → 直接收尾。**声音正常响，动画一帧都没画。**

换成 `winsound.PlaySound(SND_FILENAME | SND_ASYNC | SND_NODEFAULT)` 之后，连续三次点击都是完整的 16 帧 / 265 ms。裸调用延迟中位 0.008 ms、最差 1.855 ms。

顺带把顺序也改了：**先出声、再起表**。这样将来任何后端阻塞都不会再吃掉动画。

`SND_NODEFAULT` 是必要的——没有它，文件打不开时 Windows 会拿系统默认提示音顶替。`SND_PURGE` 在 `shutdown` 里停掉声音。

> 代价说明：`winsound` 没有音量参数，所以**放弃了 `SETTING['volume']` 那套**（只能跟随系统音量）。这是我选择后端时明确换掉的东西，不是漏做。

## 三、点击压扁：契约先行，但栽在两个设计错误上

按上一场定下的规矩，先写了一份接口契约：触发条件、时间曲线、锚点、接线顺序、验收标准、已知坑，全部列清，用户逐条确认后才动代码。（那份契约记录在开工前落盘，后来被删掉了，所以内容摘要并入本文二、三节。）

### 触发条件

用户指定按"有没有进入 dragging"判断，落地就是：

```python
was_drag = self._draging and self._dragged     # _draging 在第 10 帧翻转
plainClick = (not was_drag) and clickButton == Qt.LeftButton and self._dragRadius is not None
```

因为 `_frame_rate = 1/80`，第 10 帧 = **125 ms**。实测这条规则的分界：

```
  30 ms 触发 ✓     110 ms 触发 ✓
  60 ms 触发 ✓     130 ms 触发 ✓
  90 ms 触发 ✓     160 ms 不触发 ✗
                   300 ms 不触发 ✗
                   500 ms 不触发 ✗
```

分界**正好**在 125 ms，没有含糊。人的正常点击是 80–200 ms，所以手稍微慢一点就会被判成拖拽——这是用户指定规则的必然结果，不是 bug。

### 设计错误一：用墙钟决定动画长度

我原本写的是 `elapsed >= 0.25 就结束`。这意味着**帧数完全取决于事件循环有多忙**：

| 用户机器上观察到 | 4 帧 / 2 帧 / 17 帧（同一段代码，三次点击） |
|---|---|
| 我机器上 | 稳定 16 帧 |

根因是墙钟决定结束、定时器决定何时画，两者不一致时帧就被丢掉。改成**按帧数驱动**：

```python
SQUASH_FRAMES = 16
SQUASH_MAX_DURATION = 1.0     # 只作兜底，防止卡死

def _squashTick(self):
    self._squashFrame += 1
    if self._squashFrame >= SQUASH_FRAMES or elapsed >= SQUASH_MAX_DURATION:
        self._endSquash(); return
    scale = 1.0 - SQUASH_DEPTH * sin(pi * self._squashFrame / SQUASH_FRAMES)
```

人工加载对照（每帧额外忙等，模拟被拖慢的循环）：

| 负载 | 帧数 | 耗时 | 缩放序列 |
|---|---|---|---|
| 正常 | 16 | 269 ms | `422,406,390,377,366,358,353,351,353,358,366,377,390,406,422,439` |
| +25 ms/帧 | 16 | 512 ms | **完全一致** |
| +50 ms/帧 | **16** | 918 ms | **完全一致** |

**负载现在只会让动画慢一点，不会改变它的样子。**

### 设计错误二：挤压时画的是 GIF

按下宠物时它已经切成静态拖拽图了，松开挤压时却又变回 GIF，来回切看着像故障。改成挤压期间把标签挂静态图：

```python
# _startSquash：复用 _dragSprite 的缓存，不重新加载
self._squashPixmap = self._dragSprite(self._facingDirection)
self.petLabel.setPixmap(self._squashPixmap)

# _applySquash：逐帧缩放这张 pixmap
self.petLabel.setPixmap(self._squashPixmap.scaled(W, height, Qt.IgnoreAspectRatio, Qt.SmoothTransformation))

# _endSquash：交还给站立 GIF
self.petLabel.setMovie(self.petImage)
```

现在视觉链条是连续的：`站立 GIF → 按下：静态图 → 松开：静态图压扁弹回 → 站立 GIF`。

### 一个如实记录的偏差

底边为锚时，可见脚底仍会下沉 **+11 px**。这不是实现错误，而是贴图底部有约 52 px 透明留白的必然结果：缩到 0.8 后留白变 42 px，可见内容相对"图片底边"就下移了约 10.5 px，与实测 +11 px 吻合。锚的是**图片矩形**的底边，不是**可见像素**的底边，2.5% 量级，肉眼几乎看不出。要彻底消除得锚定每帧的可见包围盒，但 GIF 每帧内容不同会导致逐帧抖动，代价大于收益。

## 四、对话泡：位置、时序，和一次改错

### 需求与现象

用户要的是：泡泡现在**先出现在默认位置、再被挪到头顶**，希望位移完成前保持隐藏。

### 我改错了一次

我把顺序改成"先 `move()` 再 `show()`"——**在 Windows 上不成立**：一个从未显示过的顶层窗口，`move()` 会被窗口管理器在首次显示时覆盖掉，泡泡于是又回到默认位置。用户当场反馈"位置直接错了"。

正确做法是**照常 `show()`（这样 `move()` 才生效），但先用窗口透明度隐藏**：

```python
self._speechBubble.setWindowOpacity(0.0)

def placeBubble(coor, bubble=self._speechBubble):
    bubble.move(coor[0], coor[1])
    if bubble.windowOpacity() == 0.0 and self._dragRadius is None:
        bubble.setWindowOpacity(1.0)
```

### 还有一个更隐蔽的原因

即使显形时序对了，泡泡第一次出现仍在**脸上**。因为点击对话是在**按下时**创建的，此刻宠物处于"按下态"，而 `_spriteExtents()` 在按下态返回的是**相对抓取点**的包围盒。用户点在脸上，抓取点偏离贴图中心 99 px，算出的 `top` 就少了 99 px：

```
点击点偏离贴图中心 99 px
按下态（错误）位置 y = 865
站立态（正确）位置 y = 765      ← 正好差 100 px
```

所以判定里加了 `self._dragRadius is None`：**等宠物回到站立态再显形**。

验证（真实按住 150 ms 再松开）：

```
按住期间采样 22 帧，透明度全部 = 0.0     ← 全程隐形
松开后首次显形 (2104, 765) = 站立态正确位置
显形后出现过的位置只有一个
```

定时对话本来就是站立态触发的，不受影响。

## 五、GIF 白边：一个格式层面的必然结果

### 现象与排除

窗口边缘有一圈白边。用户给了关键线索：**静态 PNG 没有，GIF 有**。这一句就把范围从 Qt 合成缩到了素材本身。

### 实测

| 指标 | GIF | PNG |
|---|---|---|
| alpha 取值种类 | **2** | 256 |
| 半透明像素 | **0** | 2367 |
| 轮廓外沿像素数 | 2808 | 623 |
| 轮廓外沿平均 RGB | **(181, 180, 181)** | **(10, 5, 6)** |
| 其中接近纯白的 | 1428 个，平均 **(233, 232, 232)** | **0** |

### 成因

**GIF 只有 1 bit 透明度**——只能指定"哪个调色板索引是透明的"，没有 alpha 通道。抗锯齿的半透明边缘像素没法存，导出时必须二选一。这批素材选了"全不透明"，而那些边缘像素是**在白色背景上压平**出来的，于是颜色接近纯白，被实心保留，形成一圈沿轮廓的白毛边。PNG 的最外圈平均 RGB 是 (10,5,6)，本来就是黑色描边，所以不可能出白边。

### 处理

把"不透明 + 偏亮 + 紧邻透明"的像素，用它周围真正的画面颜色填掉（逐圈向里扩散）。不需要源工程文件。

| 项目 | 处理前 | 处理后 |
|---|---|---|
| 轮廓偏亮像素 | 1953 | **32**（−98%） |
| 轮廓平均亮度 | 180.9 | **84.7** |
| 帧数 / 总时长 | 90 帧 / 2700 ms | 33 帧 / **2700 ms** |
| 体积 | 1897.7 KB | 1939.6 KB |

90→33 是 Pillow 把**与前一帧完全一样**的帧合并了（90 帧里有 57 帧是纯重复），时长累加，播放不变——这一点我单独验证过：

```
按 30 ms 对齐比对 90 个时间点：差异超过 10% 像素的时间点 = 0
内部像素最大颜色差 = 24/255（重新量化到 255 色导致）
透明区域与原图完全一致
Qt QMovie 可读 = True
```

原文件备份为 `*.bak-whiteedge`（这个后缀程序不会加载）。

## 六、把贴图尺寸从硬编码改成读文件

原来是 `self.ORGINALWIDTH = 549` / `ORGINALHEIGHT = 549`，而文件里 19 处都写成 `self.ORGINALWIDTH * self._petImageSize` 这种派生形式，所以只改赋值那两行：

```python
self.ORGINALWIDTH, self.ORGINALHEIGHT = self._readSpriteSize()

def _readSpriteSize(self):
    for path in self.normalStates + self.dragState:
        size = QImageReader(path).size()
        if size.isValid() and not size.isEmpty():
            return size.width(), size.height()
    print("[sprite] no readable sprite size, falling back to 549x549")
    return 549, 549
```

三个取舍：

1. **用 `QImageReader`，不用 `QPixmap`/`QImage`** —— 只读文件头拿尺寸，不解码。站立 GIF 现在 2 MB / 90 帧，而这个调用发生在任何东西上屏之前，全解码会明显拖慢启动。
2. **优先站立 GIF，失败退到拖拽 PNG** —— 站立图是主素材。两者当前都是 549×549；但如果以后拖拽 PNG 换了不同画布尺寸，代码会按 GIF 的尺寸缩放它（`_dragSprite` 就是这么写的），会拉伸。这点没改，只是记下来。
3. **读不到时退回 549 并打印告警，不崩** —— 素材缺失不该让桌宠起不来。

验证：派生值 `439×439` / 窗口边长 `1242` / 内缩 `401`，与硬编码时**完全一致**；兜底路径也测了。

## 七、我犯的错（这条最重要）

### 1. 我所有诊断脚本都静音了，从没测过真实音频

这是最严重的一条。`diag_squash.py`、`diag_interference.py`、`diag_hold.py`、`diag_onscreen*.py`，**每一个**开头都写了 `pet._sfx = {}` 把声音关掉——因为我不想在测试里吵到你。

结果就是：我"验证通过"的动画，和有声音时跑的根本不是同一条代码路径。`QSoundEffect.play()` 阻塞 680 ms 这件事，在我所有测试里都被完美掩盖了。最后是用户一句"你不会是现场加载的声音导致动画帧被卡没了吧"点破的。

**教训**：替身（stub）能让测试稳定，但也会让测试失真。凡是替身掉的东西，必须至少有一条真实路径的对照。

### 2. 我改了不必改的东西

用户要的是"位移完成前保持隐藏"，这是**时序**问题。我却把 `move()` 和 `show()` 的顺序也调了，结果直接搞坏**位置**——一个我根本不需要碰的地方。修复引入了新缺陷，用户又得多测一轮。

**教训**：改动范围要贴着需求边界。要动的地方越少，出错的面积越小。

### 3. 同一个坑连踩两次

我给实例赋属性想拦截内部调用：

```python
pet._squashTick = counting_tick     # 无效
```

因为 `_squashTimer.timeout.connect(self._squashTick)` 在 `_init` 时就把**当时的绑定方法**存进槽里了，之后再改实例属性、甚至改类属性都影响不到它。两次测量脚本都因此数到 0 帧，第二次还让我误判了"帧数掉到 0"。

**教训**：替换一个已经被 `connect` 的槽，必须在 `connect` 之前动手（构造实例之前替换类方法），或者改用 `_applySquash` 这类**调用时才查找**的方法做计数点。

### 4. 屏幕抓帧的方法两次都不成立

我想验证"屏幕上真正显示的是什么"，用了 `QScreen.grabWindow(0, ...)`。第一次用 alpha 通道找内容包围盒——但桌面抓帧返回的是不透明图像，alpha 全 255，"内容高 1241" 其实是满屏，那个 0 px 变化是假信号。第二次改成"先拍一张没有宠物的背景再作差"，坐标语义又有问题，测出来的包围盒是 933 px 高，根本不是贴图。

**教训**：度量方法本身要先验证。我当时把两次都失败的结果当成了证据在推理，方向因此偏了好几轮。

### 5. 在用户已经定好规则时，我去议规则

实测发现 125 ms 阈值会让正常点击不触发之后，我直接提议"改成按位移判断"，而没先说清**当前行为就是用户指定的规则**。用户回了一句"我不是让你按照 `_frame_count` 有没有进入 dragging 判断吗？"——完全在理。

**教训**：发现规则有问题时，先讲清"这是你的规则导致的必然结果"，再谈要不要改；不能把实现偏差和规则选择混在一起说。

### 6. 一次编辑弄丢了三行（当场发现并补回）

改 `_startSquash` 时，我的替换把 `_playSound('click')`、`self._busy = True`、`self._squashFrame = 0` 三行吃掉了。写完立刻跑编译和测试发现，一分钟内补回。没有流到用户手上，但这说明我改完必须马上验证。

## 十、遗留

1. **`_endDrag` 里 `plainClick` 的判定还差最后一步**（唯一的阻塞项）。
   用户把 `and self._dragRadius is not None` 去掉了，于是 `_endDrag` 会**先清掉** `_draging/_dragged` 再算判定——安全网抢先跑时同一个长按会被拆成两次 `_endDrag`，第二次看到标志已清，就误判成点击，**真拖拽松手会偶尔多播一次压扁**，测试里这个概率是 100%（8 条红）。
   三个方案：加回守卫 / 改成 `self._frame_count < DRAG_FRAME_THRESHOLD`（我推荐，语义精确等于"有没有跨过拖拽阈值"，且不依赖会被自己清掉的状态）/ 保持现状。**等用户拍板。**

2. **`tests/test_click_behavior.py` 的拖拽用例自 `0a53b79` 起失效**。两条根因：安全网用 `QApplication.mouseButtons()` 判断按键，而合成事件不更新 Qt 内部按键状态；`_petDraggedMove()` 读的是真实光标 `QCursor.pos()`。要修得把光标来源抽成可替换的方法，属于上一场就记下的同一条遗留。

3. **`SekibankiDesktopPet.pyw` 里还留着三个调试 `print`**（`Start` / `squashing` / `end`）——那是用户自己加的，用于定位帧数问题。留着还能看帧数，确认没问题后可以清掉。

4. **`_amplifier` 仍是死设置**（上一场的遗留延续）：`config.json` 里还在读，但换成物理之后没人用。

5. **放弃的 `SETTING['volume']`**：`winsound` 没有音量参数。如果以后要音量控制，得在加载时缩放采样（`wave` + `audioop`，纯标准库）或改用其他后端。

6. **挤压幅度/时长是常量**：`SQUASH_FRAMES = 16`、`SQUASH_DEPTH = 0.2`、`SQUASH_INTERVAL_MS = 16`，想调手感应从这三处入手。
